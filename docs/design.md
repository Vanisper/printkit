# 系统设计

printkit 以本地进程提供文档产物服务，接收静态 HTML 或已有 PDF，持久化执行并提供状态查询和下载。当前交付范围覆盖 PDF 产物；系统打印队列、驱动和纸面输出在接入设备时验收。运行入口见 [README](../README.md)，外部技术依据见 [参考资料](references.md)。

## 模块与执行链路

项目使用一个 Go module。Go 标准库承担 HTTP、上下文和结构化日志，SQLite 保存任务与文档，chromedp 驱动独立 Chrome。依赖版本由 `go.mod` / `go.sum` 维护，浏览器和字体由运行环境提供。

| 模块 | 职责与接口 |
| --- | --- |
| `cmd/printkit` | 读取配置，持有数据目录锁，组装模块并协调 HTTP 与任务执行器的退出 |
| `internal/httpapi` | 校验 Host、Origin、令牌与请求，通过 `Backend` 提交任务、查询状态和读取产物，提供嵌入验证页 |
| `internal/jobs` | 管理任务规则、幂等、SQLite 事务、FIFO 执行与恢复，通过 `Renderer` 生成 HTML 产物 |
| `internal/render` | 定义排版设置，校验静态文档与资源，通过独立渲染子进程管理 Chrome、临时目录和 PDF 生成 |

```text
HTTP 提交文档
  → 校验并原子保存任务、输入和设置
  → 返回任务编号
  → 单个执行器按受理顺序领取任务
  → 使用已保存设置渲染 HTML，或保留已有 PDF
  → 原子保存产物与执行结果
  → HTTP 查询与下载
```

`httpapi` 依赖任务契约，`jobs` 消费 `render.Settings` 排版值并通过自己的 `Renderer` 接口执行，`render` 独立处理文档排版。SQLite 存储留在任务模块内，使状态、执行记录和文档的一致性在同一处维护。

HTTP 请求上下文只控制当次受理或读取，任务执行使用服务上下文。受理完成后，页面关闭或请求结束不会取消任务。一个服务只有一个执行槽位；数据库使用单连接，浏览器渲染在事务外运行，状态查询可以在渲染期间继续处理。

## 文档与排版

### HTML 输入

调用方提交完整的 UTF-8 静态打印稿。CSS 内联，图片和字体使用 data URL，表单当前值与 canvas 在提交前转换为可打印内容。通用 DOM 采集和资源打包 SDK 随真实业务接入设计。

排版保留 `@media print` 和 `@page`。默认采用 A4、四边 10 mm、缩放 1，启用背景、关闭浏览器附加页眉页脚，并优先使用 CSS 纸张尺寸。显式 `@page` 可覆盖对应页面规则。

有效设置由 `render.DefaultSettings()` 生成，在受理时序列化，与输入和任务一起保存并参与请求摘要。执行及重启恢复读取任务中的设置，校验后传入渲染器；无效设置使该次任务失败。HTTP 当前采用固定设置，尚未提供纸张参数字段。

每个 HTML 任务使用独立渲染子进程、Chrome 进程和用户目录。生成 PDF 前等待字体和图片就绪，资源错误或超时使任务失败。独立进程的冷启动和资源成本需在目标客户机测量。

文档处理有三层约束：

- 静态校验拒绝 `script`、事件属性、`noscript`、`canvas`、iframe、外链样式及 `srcset` 等输入
- 注入 CSP，并在浏览器发送请求前阻止外部网络和本地文件访问
- 保留浏览器沙箱，资源就绪检查使用服务提供的脚本，文档脚本由 CSP 禁止

data SVG 支持简单静态矢量；其中的嵌套图片、字体或样式块需转换为 PNG 或普通内联 SVG。字体家族回退到系统字体时，字形与分页可能随运行环境变化；要求稳定复现的单据应内嵌有权使用的字体，并固定浏览器与字体环境。

### PDF 输入

已有 PDF 原样保存和返回，输入与下载摘要可用于核对字节完整性。受理只检查 `%PDF-` 文件头，完整解析、密码文档及实际可打印性属于打印后端的验证范围。PDF 不应用 HTML 排版设置。

## 任务与持久化

| 状态 | 含义 |
| --- | --- |
| `queued` | 文档与任务已持久化，等待执行 |
| `rendering` | 执行器已领取任务，正在准备 PDF 产物 |
| `output_ready` | PDF 与摘要已保存，可以下载 |
| `failed` | 执行失败，任务和执行记录保留错误原因 |

任务返回 `mode: artifact`。HTML 产物表示“已生成 PDF”，PDF 输入表示“已保存 PDF”。这些状态描述文档产物的执行过程。

输入文档、排版设置和任务记录在同一个 SQLite 事务内保存，提交完成后才返回受理结果。产物、摘要、终态和执行记录同样原子保存。文档使用 BLOB 存储，状态查询只读取元数据。数据库使用 `user_version` 管理 schema，并拒绝无法识别的版本。

请求标识在调用方范围内唯一，长度为 1～128 字节，必须是有效 UTF-8，且不含控制字符和首尾空白。标题可为空，最多 256 字节，同样要求有效 UTF-8 和无控制字符。请求摘要覆盖格式、标题、有效设置及文档字节；已受理请求的重试沿用原设置判定，同键同内容返回原任务，同键不同内容返回冲突。下载摘要只覆盖 PDF 字节。

执行器按受理顺序串行执行，每次执行保留独立 attempt，包含序号、开始时间、结束时间和错误。启动时继续处理 `queued`；中断的 `rendering` 先结束原 attempt，再按任务累计恢复最多一次。恢复次数持久化，达到上限后转为 `failed`。这一恢复规则适用于生成或保存 PDF。

默认输入上限为 20 MiB，产物上限为 50 MiB，执行时限为 60 秒。执行时限覆盖浏览器启动、排版和成功产物的持久化；超时后的失败记录另用受限上下文保存。服务退出造成的执行中断保留给下次启动处理。

## HTTP 接口与授权

| 接口 | 行为 |
| --- | --- |
| `POST /v1/jobs` | multipart 上传文档与元数据；新任务返回 `202`，重复请求返回 `200` |
| `GET /v1/jobs/{id}` | 查询任务状态、执行记录和错误 |
| `GET /v1/jobs/{id}/artifact` | 下载已就绪的 PDF |
| `GET /healthz` | 查询进程是否可达 |

任务接口使用 `Authorization: Bearer <token>`。提交还需要一个 `Idempotency-Key`，multipart 正文只包含一个带文件名的 `document` 和一个 `metadata`。元数据格式如下，`kind` 只接受 `html` 或 `pdf`，`title` 可省略：

```json
{"kind":"html","title":"双联单"}
```

元数据上限为 4 KiB，整个 multipart 请求在文档上限之外允许 64 KiB 封装开销。

提交和查询直接返回任务对象，包括 `id`、`kind`、`title`、`mode`、`state`、`input_sha256`、创建/更新时间及 `attempts`。产物就绪后包含 `artifact_sha256`、`output_size` 和 `engine`；执行失败保留 `error`。下载响应中的 `X-Content-SHA256` 与任务产物摘要一致，同时提供对应 `ETag`。

接口错误使用 `{"error":{"code":"...","message":"..."}}`。状态码包括：

| 状态码 | 含义 |
| --- | --- |
| `400` | 请求格式或任务参数无效 |
| `401` | 缺少有效令牌 |
| `403` | Origin、Host 或预检请求不被允许 |
| `404` | 任务不存在或不属于调用方 |
| `409` | 请求标识冲突，或产物尚未就绪 |
| `413` | 文档、元数据或请求正文超限 |
| `500` | 内部操作失败，具体原因记录到服务日志 |

服务只监听回环 IP，并校验允许的完整 Host。每个调用方有独立随机令牌和准确的 Origin 白名单，提交、查询和下载均检查任务归属。浏览器 CORS 与调用方认证分别执行；非浏览器调用也需要令牌。

验证页位于 `/demo/`，令牌由使用者输入，只保存在页面内存中。默认 Origin 包括 `http://127.0.0.1:9148`、`http://localhost:9148` 和跨域测试来源 `http://127.0.0.1:9149`。手动验证不同本机端口时，可执行：

```sh
python3 -m http.server 9149 --bind 127.0.0.1 --directory internal/httpapi
```

打开该端口的 `/demo/`，将 API 地址设为 `http://127.0.0.1:9148`。真实 HTTPS 业务站点仍需独立验证浏览器本地网络权限、CSP、跨域和拒绝授权时的反馈。

## 配置与进程生命周期

服务通过 CLI 手动启动。系统服务安装、自启和桌面管理随部署方式扩展。

`init` 创建本地配置和 32 字节随机令牌，配置已存在时拒绝初始化并保留原文件。`token --caller <id>` 显式读取调用方令牌。省略 `--data-dir` 时，使用操作系统用户配置目录下的 `printkit`；开发入口使用 Git 忽略的 `work/dev`。

| 配置项 | 默认值或约束 |
| --- | --- |
| `listen` | `127.0.0.1:9148`，只允许回环 IP |
| `chrome_path` | 为空时查找已安装 Chrome |
| `max_input_bytes` | 20 MiB，允许不超过 100 MiB 的正数 |
| `max_output_bytes` | 50 MiB，允许不超过 200 MiB 的正数 |
| `execution_timeout_seconds` | 60，允许 1～300 秒 |
| `callers` | 每项包含唯一 `id`、独立 `token` 和准确的 `origins` |

数据目录包含 `config.json`、`jobs.db`、SQLite WAL/SHM 文件、`instance.lock` 和 `render/`。Unix 下新目录权限为 `0700`，配置和数据库为 `0600`；已有目录允许其他用户访问时，初始化或启动会失败。Windows 依赖用户目录 ACL，其权限与运行行为需要 Windows 实测。

应用在打开任务库前持有数据目录的独占执行锁，并保持到服务关闭。`jobs.Open` 的调用者负责保证独占执行；`Run` 每个实例只允许调用一次。`Close` 取消任务执行，等待已启动的执行器和渲染清理结束，再关闭数据库，并允许重复调用。

HTTP 接入与执行器由同一应用进程协调。正常退出停止 HTTP 接入，取消并等待执行器，关闭数据库后释放目录锁。结构化 JSON 日志记录任务结果、耗时，以及 HTTP 内部操作失败的关联标识和原因；令牌不写入日志。

### 浏览器资源的归属与回收

服务通过 `render.NewProcess` 创建渲染器，每次 HTML 执行启动同一可执行文件的内部渲染入口。子进程持有 Chrome，主服务只持有控制管道的写端。请求写入后管道保持打开；任务取消、服务正常退出或主服务被强制终止，都会关闭写端。子进程收到 EOF 后取消渲染，并等待 Chrome 和 allocator 清理结束。结果通过另一条管道返回，主服务等待子进程退出后才结束本次执行。

正常完成先尝试关闭 Chrome，优雅退出的等待窗口为 2 秒；取消或退出失败时仍会强制取消并等待资源清理。执行超时不会直接杀死负责清理的子进程，而是等待清理结束。内部协议限制请求和产物大小，子进程也持有执行截止时间。

`render/owner.lock` 是渲染资源的独占锁，覆盖浏览器启动、执行及清理。`render/tmp/` 只保存该数据目录的浏览器临时资源，子进程将自身临时目录指向这里，保留 chromedp 的自动用户目录与子进程清理机制。启动服务时先等待该锁并回收可安全删除的临时目录，再打开任务库、恢复任务和接收请求；旧子进程尚在清理时，新实例不会删除它的目录或启动恢复执行。

浏览器启动前将 `render/active` 写为 `active`，确认进程清理后改为 `clean`，目录删除成功后再移除标记。主服务被强杀时，仍存活的渲染子进程负责完成这一过程。目录删除失败留下的 `clean` 状态允许下次启动重试删除。

若渲染子进程自身异常退出，下一次启动发现 `active` 或无法识别的标记会保留现场并拒绝继续。此时应停止服务，确认渲染子进程及其浏览器进程树均已退出，再移除 `render/active` 并重新启动，由服务回收临时目录。`owner.lock` 保持原文件；锁释放本身不作为浏览器已退出的证据。

Windows 渲染子进程在创建 Chrome 前加入独立 Job Object。句柄不继承，异常退出由系统终止组内进程；正常清理只有确认组内仅剩渲染子进程后才解除保护。仍有子进程或无法确认状态时，报告清理失败并保留工作目录。Windows 服务账户的临时目录必须能定位到受管目录，否则启动失败。

回收只涉及所选数据目录的受管资源，不按进程名称批量终止 Chrome，也不扫描系统临时目录删除未登记的用户目录。历史任务清理和总存储配额仍属于长期驻留部署的后续工作。

## 验证范围

| 入口 | 自动化覆盖 |
| --- | --- |
| `make check` | 格式、静态分析、请求校验与授权、任务持久化与恢复、渲染进程协议及资源归属 |
| `make race` | 测试覆盖路径中的并发访问 |
| `make integration` | 实际 Chrome 的静态 HTML、资源就绪与拒绝、超时及 HTTP 产物链路 |
| `make acceptance` | 单据页数与 A4、跨域验证页、CLI 中断恢复、真实 Chrome 挂起后强杀服务的进程与目录回收 |

集成检查由 `PRINTKIT_CHROME_TEST=1` 开启，验收检查由 `PRINTKIT_ACCEPTANCE_TEST=1` 开启，均可使用 `PRINTKIT_CHROME_PATH` 指定浏览器。默认测试不依赖浏览器；CI 的 macOS 任务配置浏览器集成与验收入口。

单据验收检查双联单 1 页、50 条汇总单 3 页及 A4 页面尺寸，文字内容、字形、表头重复、裁切和整体视觉仍需逐页核对。CLI 验收在 macOS / Linux 上覆盖启动握手中断，以及挂起真实 Chrome 后强杀主服务、立即重启的场景；检查旧进程与目录退出、同一任务恢复、PDF 摘要，并确认独立浏览器仍然可用。

2026-10-27 在 macOS arm64、Go 1.26.5、Chrome 155.0.8059.85 上通过 `make check`、`make race`、`make integration`、`make acceptance`、依赖校验和本机构建。Windows amd64 / Linux amd64 的无 cgo 交叉构建，以及 Windows 生命周期测试的交叉编译通过；对应系统运行、字体及浏览器清理仍需实测。远端 CI 结果以实际工作流运行为准。

单据的人工视觉核对记录来自 2026-10-25：双联单 1 页 A4、50 条汇总单 3 页 A4，已逐页查看中文、表头重复、行分页和裁切。

业务接入使用真实双联单、汇总单及其字体和图片，与原 `window.print()` 产物逐页对照。性能测量分别记录提交受理、排版和产物可用时间，以及 Go 与 Chrome 完整进程树的 CPU、内存；阈值由客户机配置和业务等待要求确定。

## 接入系统打印队列

在 PDF 产物就绪后增加系统队列提交与查询。macOS / Linux 可先用 CUPS `lp` 验证提交，再以结构化 CUPS / IPP 接口读取状态；Windows 需要验证 PDF 到驱动的转换，例如 PDFium 配合 GDI。技术依据见 [系统打印接口](references.md#系统打印接口)。

真实打印保存系统任务编号和原始状态，区分受理、系统队列接受、系统报告结束及实际出纸。提交结果不明时进入 `unknown`，由人工核对后决定补打。产物自动恢复只承担 PDF 的重新生成，系统队列提交需要自己的恢复与去重契约。

进入设备验证前，需要业务样本、实际纸张、字体、目标 HTTPS 来源和首套设备环境。随后按部署需求扩展平台、设备和无人登录运行方式。
