# 最小原型方案

Go 软件原型已实现文档提交、持久化、生成 PDF、查询和重启恢复，当前运行验证以 macOS 开发机为准。目前没有可用打印机；真实队列、驱动和纸面输出留到设备阶段验收。本文记录实现边界、接口及验证结果，启动命令见 [README](../README.md)。

## 选型结论

| 语言 | 与当前任务的关系 | 本次选择 |
| --- | --- | --- |
| Go | 主要工作是 HTTP、任务存储、调度和浏览器进程管理，标准库及现有组件可以直接承担 | 作为主服务语言 |
| Rust | Windows 原生接口绑定是明确优势，但当前原型还不涉及驱动和 PDF 原生库 | 后续原生后端复杂时再比较 |
| Zig | 适合有明确需求的底层组件，当前需要额外承担工具链和接口迁移 | 本轮不采用 |

选择 Go 是对当前工作量和维护成本的判断，未做语言性能排名。HTML 排版仍交给浏览器，语言选择不会消除其运行成本。原生打印将来可以在 Go 内实现，也可以由独立工作进程承担；现在保持一个 Go module。依据见 [技术选型调研](references.md#技术选型依据2026-10-24)。

## 技术组合

| 部分 | 确定采用的方案 | 目的 |
| --- | --- | --- |
| 主程序 | Go，标准库 `net/http`、`context`、`log/slog` | 一个可直接启动的本地进程 |
| HTML 渲染 | chromedp + 独立 headless Chrome | 复用现有 HTML/CSS，通过 CDP 生成 PDF |
| 持久化 | `database/sql` + `modernc.org/sqlite` | 保存任务、执行记录、输入和产物，首期保持无 cgo 构建 |
| 调度 | 一个持久化队列、一个执行槽位 | 先明确顺序、恢复和资源使用 |
| Web 通信 | 本机 HTTP + JSON / multipart，轮询查询 | 先完成提交和查询，避免长连接生命周期占用原型工作量 |
| 验证界面 | 普通 HTML / JavaScript 页面 | 提交样本、查看状态、下载 PDF |
| 输出 | PDF 产物模式 | 在没有打印机时验收软件链路 |

依赖固定在 `go.mod` 和 `go.sum`：Go 工具链为 1.26.5，chromedp 为 0.21.0，SQLite 驱动为 1.61.0。浏览器可自动查找或通过 `chrome_path` 指定，每次执行记录浏览器版本并使用独立用户目录。开发机验证使用 Chrome 155.0.8059.85；可重复的基准测试还需固定浏览器与字体，不能只固定 Go 依赖。

本轮由命令行手动启动服务，网页关闭后服务继续工作。系统服务安装、自启、托盘和完整桌面界面在后续运行方式验证中实现。

## 一条最小链路

```text
验证页提交 HTML / PDF
  → 校验并持久化任务
  → 返回任务编号
  → 单个执行器生成或保存 PDF
  → 持久化产物与结果
  → 验证页查询、下载
```

### 输入与排版

HTML 输入限定为业务已准备好的静态打印稿：CSS 内联，图片和字体以 data URL 携带，表单当前值与 canvas 已转换为可打印内容。原型先接受一个完整 HTML 文件，通用 DOM 采集和资源打包 SDK 留到真实业务接入时实现。

保留现有 `@media print` 与 `@page` 规则。渲染时启用背景、关闭浏览器附加页眉页脚，采用 CSS 纸张尺寸优先，缺省 A4；将有效的渲染选项随任务保存。字体和图片就绪后才生成 PDF，资源失败和超时返回具体错误。

缺省边距为四边 10 mm，缩放为 1；显式 `@page` 可覆盖页面规则。当前没有单独的纸张设置 API，固定选项与输入文档共同参与去重摘要。

每个 HTML 任务启动独立 Chrome 进程和用户目录，结束后清理其子进程，先测量冷启动成本。载入单据前限制脚本和资源访问，禁止单据脚本、外部网络请求和任意本地文件访问，保留浏览器沙箱。出现被阻止资源、字体或图片加载失败时任务失败；后续有测量依据时再考虑浏览器进程复用。

静态校验拒绝 `script`、事件属性、`noscript`、`canvas`、iframe、外链样式和 `srcset` 等动态输入；canvas 和表单当前值需在业务侧转成静态内容。文档首部注入 CSP，并通过浏览器请求拦截阻止外部资源。资源检查只运行服务提供的脚本，文档脚本仍被 CSP 禁止。data SVG 限于简单静态矢量，嵌套图片、字体或样式块需转换为 PNG 或普通内联 SVG。

当前使用系统字体的样本只能证明开发机排版正确。需要稳定复现时，应随文档内嵌有权使用的字体；字体家族回退到系统字体时，原型不保证字形与其他平台一致。

已有 PDF 原样保存并返回，校验传输完整性与内容摘要。此路径只验证文档接收和存储，完整 PDF 解析、密码文档及实际可打印性在打印后端接入时处理；不会对它重新套用 HTML 排版选项。

### 任务与存储

任务状态先限定为 `queued`、`rendering`、`output_ready` 和 `failed`。`output_ready` 的含义是 PDF 已保存且可以下载。查询同时返回 `mode: artifact`，HTML 输入显示“已生成 PDF”，PDF 输入显示“已保存 PDF”。本轮没有系统任务编号或设备完成状态。

输入文档、设置和任务记录在同一个 SQLite 事务内保存，再返回受理结果。PDF 产物与 `output_ready` 也在同一事务内写入。先用 BLOB 保存小批量样本，查询状态时只读取元数据；大文档存储在取得真实样本后再调整。

初始保护配置为输入最多 20 MiB、产物最多 50 MiB、每次执行最多 60 秒。执行超时覆盖浏览器启动、排版及产物保存，失败时清理进程和临时资源；这些是可调整的运行上限，业务响应目标另行测量。

请求标识在调用方范围内唯一，摘要覆盖文档和设置。相同请求返回原任务；相同标识携带不同内容时返回冲突。任务执行的生命周期由服务持有，提交请求结束或页面关闭后仍继续。

请求标识为 1～128 字节，不含控制字符和首尾空白；标题最多 256 字节。去重摘要包含格式、标题、固定设置和文档字节，下载摘要只包含 PDF 字节。标题不同也会被视为不同请求内容。

执行器从数据库领取任务，每次执行保留独立记录。重启后继续处理 `queued`；中断的渲染先记录该次失败，再重新执行。文件产物模式下这一步没有打印副作用，按任务累计自动恢复最多一次，计数持久化；持续失败转为 `failed`。已提交真实打印队列后的恢复另行设计。

### HTTP 接口与授权

| 接口 | 行为 |
| --- | --- |
| `POST /v1/jobs` | multipart 上传 `document` 文件和 `metadata` JSON，使用 `Idempotency-Key`；新任务返回 `202`，相同请求返回 `200` |
| `GET /v1/jobs/{id}` | 返回当前状态、执行记录和错误，页面定时查询 |
| `GET /v1/jobs/{id}/artifact` | 授权后下载已保存的 PDF |
| `GET /healthz` | 判断进程是否可达 |

`metadata` 格式为 `{"kind":"html","title":"双联单"}`，`kind` 只接受 `html` 或 `pdf`。接口使用 `Authorization: Bearer <token>`；上传文件字段必须带文件名。元数据上限为 4 KiB，整个 multipart 请求额外允许 64 KiB 的封装开销。

提交和查询直接返回任务对象，包括 `id`、`kind`、`title`、`mode`、`state`、创建/更新时间及 `attempts`。产物就绪后包含 `artifact_sha256`、`output_size` 和 `engine`；执行失败保留 `error`。下载响应中的 `X-Content-SHA256` 与任务摘要一致。错误响应统一为 `{"error":{"code":"...","message":"..."}}`：无效输入 `400`、缺少有效令牌 `401`、不允许的 Origin/Host `403`、不存在或不属于调用方的任务 `404`、幂等冲突或产物未就绪 `409`、输入超限 `413`。

服务只监听回环地址，配置允许的准确 Origin，并给每个调用方生成独立随机令牌。开发验证页手动输入令牌；提交、查询和下载都检查调用方归属，令牌不写进示例源码。浏览器 CORS 配置与服务授权分别验证。

验证页嵌入可执行文件，通过 `/demo/` 打开。默认允许 `http://127.0.0.1:9148`、`http://localhost:9148` 和跨域测试来源 `http://127.0.0.1:9149`；其他来源需显式加入对应调用方的配置。跨域测试可用 `python3 -m http.server 9149 --bind 127.0.0.1 --directory internal/httpapi` 提供页面，打开该端口的 `/demo/` 后将 API 地址改为 `http://127.0.0.1:9148`。

真实 HTTPS 业务站点访问本机，还需单独验证浏览器本地网络权限、CSP 与拒绝授权时的反馈；本地验证页通过不能替代这一项。

### 配置与进程生命周期

`init` 创建本地配置和 32 字节随机令牌，不覆盖已有配置。`token --caller <id>` 显式读取对应调用方令牌；启动日志不包含令牌。省略 `--data-dir` 时使用操作系统用户配置目录下的 `printkit`，仓库开发使用已忽略的 `work/dev`。

| 配置项 | 缺省值或约束 |
| --- | --- |
| `listen` | `127.0.0.1:9148`，只允许回环 IP |
| `chrome_path` | 空字符串时查找已安装 Chrome |
| `max_input_bytes` | 20 MiB，可设置为不超过 100 MiB 的正数 |
| `max_output_bytes` | 50 MiB，可设置为不超过 200 MiB 的正数 |
| `execution_timeout_seconds` | 60，可配置 1～300 秒 |
| `callers` | 每项包含唯一 `id`、独立 `token` 和准确的 `origins` |

数据目录包含 `config.json`、`jobs.db`、SQLite 的 WAL/SHM 临时文件和 `instance.lock`。Unix 下新目录权限为 `0700`、配置和数据库为 `0600`；已有目录允许其他用户访问时拒绝初始化或启动。Windows 使用用户目录 ACL，其权限和运行行为需在 Windows 实测。

同一数据目录只能由一个进程持有执行锁。正常退出会停止 HTTP 接入并取消后台任务，等待执行器结束后关闭数据库并释放锁；正在渲染的任务留待启动恢复。日志为结构化 JSON，记录任务编号、耗时和错误。原型尚无历史清理与总存储配额，测试数据按专用目录管理。

正常退出和任务超时会回收 Chrome。`SIGKILL` 无法运行进程内清理，可能留下 Chrome 子进程与临时用户目录；启动恢复目前只恢复持久化任务，不自动回收上次强制终止的浏览器资源。该边界需在长期驻留部署前补齐，不能把任务恢复通过视为异常资源回收已完成。

## 代码组织

代码保持一个 Go module，目录按实际职责组织：

```text
cmd/printkit/             启动、配置和退出处理
internal/jobs/           任务规则、SQLite 存储、调度和恢复
internal/render/         Chrome 生命周期、HTML 排版与资源就绪
internal/httpapi/        请求解析、授权、提交和查询
internal/httpapi/demo/   最小验证页面
testdata/                合成双联单与多页汇总单
.github/workflows/       三平台检查、无 cgo 构建和 Chrome 集成检查
```

对外围绕提交、查询和读取产物组织接口。存储随任务模块实现，浏览器细节收在渲染模块；真实打印后端出现后再增加对应模块。本轮不预设多语言核心库或插件协议。

`cmd` 组装模块；`httpapi.Backend` 表达提交、查询和下载契约，`jobs.Renderer` 表达 HTML 转 PDF 契约。HTTP 请求上下文只控制受理，worker 使用服务上下文。SQLite 只保留一个连接，事务结束后才启动浏览器，避免长时间渲染阻塞查询；schema 通过 `user_version` 管理并拒绝无法识别的新版本。

## 验证范围

| 链路 | 实现内容 | 验收依据 |
| --- | --- | --- |
| 1. PDF 接收 | HTTP、SQLite、请求去重、PDF 产物下载 | 上传与下载摘要一致，重复请求只生成一个任务，重启后仍可查询 |
| 2. HTML 渲染 | 静态 HTML、字体与图片检查、Chrome 生命周期 | 双联单和汇总单的 PDF 内容、分页、纸张和字体人工核对 |
| 3. Web 验证 | 验证页、跨域授权、轮询和错误呈现 | 页面持续可操作，关闭后任务继续，未授权请求被拒绝 |
| 4. 恢复与测量 | 渲染超时、进程退出、执行恢复、耗时记录 | 中断不丢受理任务，失败可追溯，自动恢复有上限 |

先用脱敏样例跑通功能，取得业务实际样本后，与原 `window.print()` 另存的 PDF 对照内容、分页、纸张和中文字体，并核对下载产物的摘要；样例通过只代表样例范围。分别测量提交受理、排版、产物可用时间及 Go 与 Chrome 的 CPU、内存，阈值根据实际客户机和业务等待要求确定。

自动化检查覆盖请求冲突、并发重复提交、重启恢复和授权归属；HTML 集成检查使用实际 Chrome。排版用 PDF 页面人工对照，测试替身只用于稳定复现错误和中断。

2026-10-25 在 macOS arm64、Go 1.26.5、Chrome 155.0.8059.85 上完成默认测试、vet、race 和实际 Chrome 集成检查。双联单生成 1 页 A4，50 条汇总单生成 3 页 A4，已逐页查看中文、表头重复、行分页和裁切。PDF 上传下载逐字节一致。浏览器验证通过同源与不同本机端口来源的提交、下载摘要校验，以及离开页面后重新按编号查询。Windows amd64、Linux amd64 的 `CGO_ENABLED=0` 交叉构建通过；对应系统运行、Chrome 子进程清理和字体表现尚未实测。CI 文件已配置，远端运行结果在推送后确认。

真实 CLI 中断检查在 `rendering` 时强制终止主进程，重启后获得同目录执行锁，第一次执行记录中断，第二次生成可下载 PDF；再次启动没有重跑已完成任务。此检查由脚本清理残留 Chrome，未验证服务自动回收强制终止遗留资源。

## 接入真实打印的下一步

有设备后，选择实际可用的系统队列。macOS / Linux 可以先用 CUPS `lp` 验证提交，再以结构化 CUPS / IPP 接口查询任务；Windows 需要验证 PDF 到驱动的转换，例如 PDFium 配合 GDI。原生后端的实现语言根据真实接口工作量选择，具体依据见 [打印后端调研](references.md#后续打印后端)。

真实打印时，在 PDF 产物准备完成后增加提交和队列查询。持久化系统编号与原始状态，明确区分受理、系统队列接受、系统报告结束和实际出纸；提交结果不明时进入 `unknown`，由人工核对后决定补打。产物模式的自动恢复规则仅适用于重新生成 PDF。

当前仍需补齐的是业务样本、实际纸张、字体及目标 HTTPS 来源。取得这些输入后，先复核软件产物和客户机表现，再接入真实打印队列。
