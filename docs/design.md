# 打印方案与验证

本文是当前候选方案，尚未实现或实测。目标与阶段范围见 [README](../README.md)。

## 打印流程

首个原型采用以下候选路径：

```text
业务准备打印稿 → 本地服务受理任务 → HTML 渲染为 PDF → 系统队列与驱动 → 打印机
```

已有 PDF 可以直接进入打印后端。任务受理后返回编号，调用方通过该编号查询进展；排版和打印在后台继续执行。

先在同一仓库内分清四项职责，具体目录随所选语言确定：

| 部分 | 负责的事情 |
| --- | --- |
| 接入 | 接收文档和打印设置、识别调用方、返回任务编号与查询结果 |
| 任务执行 | 持久化、调度、执行记录、恢复与补打 |
| 文档渲染 | 将 HTML、样式和资源排版为固定 PDF |
| 打印后端 | 枚举系统队列、校验设置、调用驱动、读取队列反馈 |

Web 接入与后续桌面、CLI 入口共用任务行为。后台执行与管理界面分离，渲染进程独立运行，以便限制资源占用并处理超时或崩溃。公开库、包和插件边界等到出现实际复用需求时再划分。

## 文档与打印设置

业务继续负责形成打印稿，包括双联内容、字段取舍、按钮隐藏和打印样式。移交给本地服务的内容需要足够完整，能够在原页面关闭后重新排版：

- 单据 HTML、打印 CSS，以及纸张、边距和缩放设置
- 已转为打印内容的表单当前值、canvas 图像等动态状态
- 字体、图片及其他资源，优先随文档提交

需要从外部读取资源时，应明确访问权限、有效期和加载失败的处理方式。默认使用静态打印稿；业务脚本和浏览器登录态不随文档继承。资源缺失、加载超时或排版失败时返回具体错误。

目标打印机、纸张、方向、份数等设置随请求明确提交。设备绑定将业务中的打印目标对应到一个系统队列；队列不可用或设置不受支持时，交由调用方处理。

PDF 固定了排版，仍需由打印后端转为驱动可处理的内容。验证时要记录实际的转换路径及依赖，尤其是 Windows 的 PDF 渲染路径和 CUPS 的过滤链。[Windows RAW 数据类型](https://learn.microsoft.com/en-us/windows-hardware/drivers/print/raw-data-type)、[CUPS 设计](https://www.cups.org/doc/spec-design.html)

## 任务与结果

一次打印请求形成一个 printkit 任务，每次实际执行保留独立记录。取得系统队列任务编号时一并关联，未取得时保留提交结果与可用的状态依据。任务保存文档、打印设置和执行历史，人工补打创建关联原任务的新任务。

查询结果应说明当前阶段以及判断依据：

| 结果 | 含义 |
| --- | --- |
| 已受理 | 请求通过校验，文档及必要资源已经持久化 |
| 处理中 | 正在准备文档、渲染或提交系统队列 |
| 已提交队列 | 系统打印队列已接受任务 |
| 系统报告结束 | 队列反馈执行结束，保留原始状态及来源 |
| 失败 | 已确认的失败，附出错阶段和原因 |
| 结果待确认 | 可能已经提交或输出，当前证据不足 |

实际出纸以设备反馈或人工核对为依据。队列接受、队列消失和系统报告结束所能确认的范围，取决于系统与驱动。[Windows 队列状态](https://learn.microsoft.com/en-us/windows/win32/printdocs/job-info-2)

重复请求在调用方范围内按请求标识去重，返回原任务；同一标识对应不同内容或设置时报告冲突。重试只适用于能够确认尚未产生打印副作用的情况。提交中断、部分出纸或提交后记录丢失时，先核对状态，无法确定则等待人工处理，避免自动重复打印。

## Web 接入与后台运行

Web 接入先验证目标浏览器中的本机通信，候选为 HTTP 或 WebSocket。授权需要覆盖调用方和可用打印范围，并支持撤销；完成授权后，每次提交无需再打开打印对话框。本地接口只提供定义好的打印操作，资源访问和输入大小有明确限制。

原型需要同时验证 HTTPS 业务页面访问本地服务、首次授权、拒绝未授权调用，以及服务不可用时的错误反馈。CORS 配置与调用授权分别处理。

后台服务持有已受理任务，网页和管理界面的退出不影响执行。无人登录时的新任务由仍在运行的调用方提交，也可以处理此前已持久化的任务。

Windows 系统服务、macOS LaunchDaemon 和 Linux 系统服务是对应的候选宿主。验证须使用服务实际账号，检查队列、字体、资源和存储权限；已登录、锁屏、注销、冷启动后未登录分别记录结果。

## 验证顺序

先在一个真实部署环境跑通链路，再扩大支持范围。首个原型可以使用便于验证的工具；长期选型前，对其他平台的驱动接口和无人登录宿主做小规模可行性验证。

| 步骤 | 要回答的问题 | 留下的结果 |
| --- | --- | --- |
| 1. 建立基线 | 现有双联单和汇总单的排版、响应与等待情况如何？ | 脱敏样本、打印设置、环境信息、原流程测量记录 |
| 2. 固定 PDF 打印 | 指定队列能否按设置准确输出？ | 转换路径、系统任务编号、纸面核对结果 |
| 3. HTML 排版 | 现有打印稿迁移后内容和分页是否一致？ | 生成的 PDF、字体与图片检查、布局差异 |
| 4. Web 提交 | 授权页面能否异步提交、查询，关闭后任务能否继续？ | 浏览器与授权结果、端到端执行记录 |
| 5. 异常恢复 | 重复请求、离线和进程中断后是否会丢任务或误重打？ | 故障记录、恢复结果、待确认任务的处理方式 |
| 6. 扩展环境 | 其他平台、服务账号和无人登录条件下能否运行？ | 各部署组合的通过、失败或未验证记录 |

纸面核对覆盖内容、双联标记、分页、纸张尺寸、缩放、边距和份数；样本中存在条码时一并检查可读性。异常验证至少覆盖缺纸、设备离线、资源加载失败，以及提交前、提交中和队列接受后的进程退出。

在同一台客户机上对比新旧流程，分别测量文档准备、渲染、队列提交和首张出纸，记录页面响应及整条链路的 CPU、内存占用。人工确认的等待时间单列，冷启动与重复执行分开测量。可接受阈值根据业务基线确定。

首个原型以两份真实单据完成正确输出、异步状态查询和异常恢复为验收重点；后续每增加一个平台或运行条件，都补充相应的驱动和实际出纸验证。

## 当前待定

- 首批环境：客户机配置、操作系统、浏览器、打印机、驱动和纸张规格
- 业务验收：允许的排版差异、响应目标，以及由谁处理结果待确认和补打
- 实现工具：Go、Rust 或 Zig 等核心语言，HTML 渲染器、PDF 打印后端与存储方式

语言和框架的选择以原型结果、跨平台可行性及维护成本为依据。安装、升级和分发细节在运行方式确定后再展开。
