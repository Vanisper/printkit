# 需求与范围

更新日期：2026-09-29。本文区分已确认需求、阶段建议和待验证条件，避免把技术提议误写成产品承诺。

## 产品定位

printkit 是独立的通用本地打印系统。可复用的打印能力是核心，后台服务、桌面管理工具、Web 接入与其他软件接入围绕该能力展开。

产品目标是改善现有方案在接入体验、运行响应、跨平台覆盖、打印控制与维护方面的实际表现。是否优于参考项目，需要在明确场景下验证。

## 已确认需求

| 维度 | 要求 |
| --- | --- |
| 项目 | 名称为 `printkit`，在独立目录和仓库中开发 |
| 服务对象 | 当前业务 Web，以及未来的桌面应用、CLI、SDK 和其他调用方 |
| 目标系统 | Windows、macOS、Linux |
| 设备连接 | USB 与局域网，优先通过系统驱动打印 |
| 自动运行 | 已登录时关闭网页仍能工作；无人登录时也能执行已有或其他入口提交的任务 |
| 交互 | 已授权应用可以按明确的打印意图静默打印 |
| 桌面形态 | 可以独立发展为用户管理打印的桌面软件 |
| 集成 | 可与 weblauncher 组合，但不在 weblauncher 中实现产品核心 |
| 扩展 | 支持围绕核心能力发展多个库或模块；Go、Rust、Zig 均可评估 |
| 后续能力 | 保留后台远程派发、Web 拖拽模板设计的需求，优先处理当前本地单据场景 |

无人登录执行不意味着已关闭的业务网页还能继续产生新任务。任务必须已持久化，或由仍然运行的调用方提交。

## 当前业务场景

业务 Web 已经具备单据页面，包含双联收购订单和汇总表。现有实现使用打印媒体样式，克隆打印区域到 iframe，补全样式后调用该 iframe 的 `window.print()`。

参考截图中，屏幕页面带有输入控件、选择按钮、颜色和页面缩放；打印稿则有独立的样式、字段呈现和纸张布局。迁移时应保留现有“如何形成打印稿”的业务规则，而不是把整个业务页面当作通用打印模板。

当前问题包括：

- 每次打印需要进入浏览器打印交互
- 业务代码难以得到具有明确含义的任务回执和后续状态
- 低配置机器打开打印预览可能卡顿、缓慢
- 已确定的打印机与打印参数难以作为业务配置稳定复用

`window.print()` 的等待行为不能泛化成所有浏览器中所有页面进程必然完全冻结。项目需要测量实际使用的浏览器、版本和设备表现。[HTML 打印规范](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#printing)

## 首阶段建议

首先验证当前业务能否将独立、可重放的打印文档交给本地系统，并完成静默提交、状态查询和故障恢复。

| 工作项 | 阶段目标 |
| --- | --- |
| 文档接入 | 现有 HTML/CSS 单据的受控接入，以及固定 PDF 输入 |
| 设备管理 | 发现可访问队列、明确绑定、查询能力、验证打印设置 |
| 任务管理 | 持久化接收、执行记录、查询与事件通知、明确补打 |
| 原生打印 | 三平台代表性驱动和设备验证，不预先承诺所有机型 |
| Web 接入 | 确认来源授权与浏览器兼容后的本地通信 |
| 运行方式 | 后台核心与用户界面分离，分别验证登录和无人登录 |
| 用户工具 | 最小配置、状态和诊断入口，后续再扩展完整桌面管理 |

无需先建设中央任务服务器，才能执行本地打印；也无需先重建模板设计器，才能复用业务已有打印稿。

## 后续扩展

- 可视化模板设计、字段绑定与模板版本管理
- 远程任务派发、站点管理与集中运维
- 更多文档输入、设备指令与厂商专用能力
- 桌面文档管理、打印历史和更完整的用户工作流
- 核心库对其他语言的嵌入式调用

这些扩展通过各自的需求与验证决定实现顺序，不提前变成首版依赖。

## 产品边界

当前方向是由调用方明确提交打印任务。安装 printkit 不会自动赋予任意网页本机权限，也不等于接管任意应用的系统打印操作。

首阶段不开发虚拟打印机驱动，不承诺任意网页 DOM 无损导出，不承诺所有机型都能证明实际出纸，也不以物理打印严格恰好一次作为可普遍保证的行为。

优先使用系统驱动意味着依赖目标系统存在合适的驱动或可用队列；跨平台客户端不等于所有打印机都具有跨平台驱动。

## 待决问题

1. 首批操作系统版本、CPU 架构、Linux 发行版、代表机型和驱动版本是什么？
2. 低配置客户机的实际硬件、浏览器版本和可接受响应目标是什么？
3. 首批纸张规格、套打精度、双面和自定义纸张要求有哪些？
4. 能否直接复用当前生成打印 DOM 的函数，哪些资源需要鉴权或动态生成？
5. “打印完成”在业务中要求到哪一层；结果待确认时由谁决定补打？
6. 多个系统用户、多个业务应用之间的设备配置、任务查看与操作权限如何分配？
7. 本地文档与历史保留多久；哪些内容可进入诊断包？
8. 首版的安装权限、升级方式、商业分发方式和许可证如何确定？

这些问题影响实现与验收细节；目前不据此虚构兼容范围、性能指标或技术栈结论。
